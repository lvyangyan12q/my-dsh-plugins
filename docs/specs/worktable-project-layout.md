# Worktable 项目布局落盘与恢复调整方案

每个项目固定使用一份 `.dsh-worktable/layout.json`。有项目目录时，文件是布局的主要存储，浏览器 localStorage 保留为缓存及兼容来源。第一阶段交付保存、恢复和旧数据保护；新增布局样式分别验证。

用户已确认上述文件约定，以及“真实安装后调整布局、确认落盘、关闭重开恢复、清空专用测试浏览器缓存后从目录恢复”的主验收入口。本文登记到现有本地 Markdown 跟踪器；`ready-for-agent` 表示可据此实施，不表示代码已经修复或功能已经验收。下面的具体格式、写入协议和分阶段步骤是本方案的实施设计，不冒充逐项已经获得用户确认。

## Problem Statement

工作台的项目布局原来主要依赖浏览器 localStorage。项目目录虽然保留了页面、脚本和产物，却不能单独恢复工作台中的窗格结构、标签与尺寸；更换浏览器、清除缓存或重新添加项目后，用户需要重新配置。

本轮未提交代码已尝试把布局写入项目目录，但仍以工作台内部项目 ID 组成文件名，读取也要求当前 ID 相同。这使布局文件继续依赖浏览器中的项目登记信息，无法自然形成“选择项目目录即可找回布局”的使用方式。

现有候选仍存在几处需要一并修复的缺口：拖动尺寸没有触发文件保存；防抖任务执行时读取全局当前尺寸，切换项目后可能保存错尺寸；路径拼接写死 Windows 分隔符；文件读取失败被合并为无文件，并可能继续写入；文件写入没有布局级原子提交和并发保护。

前次核对还发现分栏高度计算使用尚未初始化的变量。本次文档交付读回时，共享工作区中的该表达式已改为直接使用根区域顶部坐标；本次未修改这段源码，也未运行验证，实施时须以最新源码确认并回归，不重复套用旧补丁。

## Solution

用户配置或选择一个项目目录后，工作台始终在该目录使用同一份布局文件。文件名不随浏览器中的项目登记 ID 改变，也不因为选择了新的布局预设而创建另一份主布局文件。

正常使用时，窗格、标签和尺寸变更自动保存。界面区分正在保存、已经保存、未保存和冲突，只有确认写入成功后才显示已经保存。关闭项目并重新打开时从文件恢复；在新的浏览器环境中，用户选择已有项目目录即可恢复登记和布局。

没有目录的项目继续使用原 localStorage。原生会话、应用实例、业务数据和页面内部状态仍由各自模块负责；布局文件保存它们的引用，不能被描述为完整项目数据备份。

### 恢复与兼容规则

| 读取结果 | 工作台行为 | 是否允许自动写主布局文件 |
| --- | --- | --- |
| 主布局文件存在且兼容 | 按文件恢复结构、标签和尺寸，并更新该项目缓存 | 允许后续正常变更保存 |
| 主文件不存在，能明确识别一个属于本项目的兼容旧文件 | 校验后迁移；写入成功再采用新主文件；保留旧文件 | 仅允许不覆盖已有主文件的迁移创建 |
| 主文件和兼容旧文件均不存在，当前已有浏览器布局 | 从本项目布局与尺寸缓存生成首份文件，写入成功后成为主存储 | 允许创建；若创建期间已出现文件，转冲突处理 |
| 用户选择的目录没有布局，也没有可用缓存 | 显示正常的新建布局入口，不声称已经恢复 | 用户完成布局创建后允许保存 |
| 文件损坏、版本不兼容或读取失败 | 保留文件；有缓存时允许带明确提示临时展示；提供重试入口 | 禁止用缓存自动覆盖 |
| 发现多个归属不明确的旧文件，或文件身份与已有项目冲突 | 显示候选和原因，等待用户明确选择恢复对象 | 禁止按文件时间或目录扫描顺序擅自覆盖 |

## User Stories

1. 作为工作台用户，我希望一个项目只有一份主布局文件，以便直接在项目目录中找到和保存布局。
2. 作为工作台用户，我希望文件名固定，以便重新添加项目时无需知道旧浏览器里的项目 ID。
3. 作为工作台用户，我希望窗格数量、所在位置和标题能保存，以便重新打开后继续原来的工作安排。
4. 作为工作台用户，我希望标签内容引用、标签顺序和选中标签能保存，以便回到原来的页面或工具。
5. 作为工作台用户，我希望聊天宽度、左列宽度、顶行高度和可调整的窗格宽度能保存，以便不必每次重新拖动。
6. 作为工作台用户，我希望仅拖动分隔条也能保存，以便不需要再修改标签来触发落盘。
7. 作为工作台用户，我希望看到保存失败和重试结果，以便知道关闭页面前还有哪些变化未写入文件。
8. 作为工作台用户，我希望关闭重开或重启测试宿主后恢复布局，以便确认布局确实保存在磁盘上。
9. 作为工作台用户，我希望在新的浏览器环境选择已有项目目录即可恢复布局，以便摆脱旧缓存依赖。
10. 作为工作台用户，我希望旧项目和没有目录的项目仍能使用，以便逐步采用文件保存。
11. 作为工作台用户，我希望旧的按项目 ID 命名的布局能够迁移，以便保留本轮已经配置好的工作环境。
12. 作为工作台用户，我希望坏文件和不兼容文件被保留，以便排查或恢复，而不是被默认布局覆盖。
13. 作为同时操作多个项目的用户，我希望快速切换项目不会混用内容和尺寸，以便每个文件只保存自己的布局。
14. 作为使用多个浏览器标签页的用户，我希望旧页面不能覆盖较新的布局，以便已有修改不会悄悄丢失。
15. 作为使用布局脚本的用户，我希望脚本与界面使用同一文件格式和写入规则，以便两种调整方式可以配合使用。
16. 作为重新打开项目的用户，我希望缺失应用、失效文件或不可用会话有明确提示，以便保留布局并修复引用。
17. 作为工作台用户，我希望移除侧栏登记或关闭项目不会删除布局文件，以便之后可以从目录重新恢复。
18. 作为不同平台的用户，我希望路径使用项目现有的跨平台约定，以便目录保存不依赖手写的 Windows 分隔符。

## Implementation Decisions

### 1. 存储归属与目录

- 每个项目目录只有一份当前主布局，固定为 `.dsh-worktable/layout.json`。历史备份和迁移来源可以保留，但不作为第二份自动读写的主布局。
- 新格式去掉按浏览器项目 ID 生成文件名的规则。固定路径是文件格式契约，不依赖项目显示名或预设名。
- 同一物理目录只有一个布局写入目标。发现已有登记时复用或提示已有项目，不为重复登记悄悄初始化另一份布局，也不合并不同项目身份。
- 不在后台扫描全盘目录。无缓存恢复由用户选择项目目录触发，读取布局后恢复必要的项目登记信息。
- 无目录项目继续保留原有浏览器保存方式；添加目录时先检查该目录已有布局，不能直接用缓存覆盖。

### 2. 布局文件内容与引用边界

建议新主文件使用独立的版本 2 格式，与当前按 ID 命名的版本 1 候选明确区分。文件包含以下信息：

| 内容 | 约定 |
| --- | --- |
| `version` | 文件格式版本；不认识的版本拒绝写回 |
| `revision` | 每次成功提交递增；用于受支持写入方的冲突检查 |
| `savedAt` | 保存时间，供展示和诊断；不单独用于判断谁覆盖谁 |
| `project` | 稳定项目身份和恢复登记所需的名称；目录取当前用户选择的实际目录，不依赖旧绝对根路径 |
| `spec` | 窗格结构、窗格身份、标题、折叠状态、标签引用及顺序、选中标签、聊天位置与布局选项 |
| `geometry` | 聊天和左列宽度、顶行高度、各可调整窗格的宽度；按窗格身份或经校验的列表对应 |

文件中的项目身份用于维持引用关系，不能再要求它与尚未恢复的浏览器随机 ID 相同才允许读取。恢复登记时保留稳定身份；如果本地已有同身份的其他目录，报告冲突，不擅自换 ID 或重绑应用。

应用、实例、视图、原生会话、终端和自定义产物只保存布局所需引用与声明配置。不得序列化运行句柄、权限、凭据或整份业务资料。引用的资源不在当前宿主时保留原标签并显示不可用，不自动创建实例或启动进程来伪装恢复成功。

复制项目目录不等于复制了应用实例和会话；创建独立项目副本与引用重映射不在本轮范围内。

### 3. 一个布局存储模块负责读写

- 将读取、版本校验、旧格式转换、写入、冲突处理和结果分类集中在布局存储模块。工作台界面负责读取结果展示和提交布局快照；分栏引擎继续负责渲染与布局操作。
- 布局专用服务沿用宿主现有认证准入和文件权限约定，由服务端根据项目目录推导固定目标。不能把现有通用文件写入的成功响应当作已经完成布局级并发和原子保存。
- 读取结果区分存在、明确不存在、无权限、暂时失败、损坏、版本不兼容及身份冲突。只有明确不存在才允许初始化，不能把所有异常归并为空值。
- 保存请求携带完整快照和预期修订。返回提交后的修订或明确失败类型；失败保留上一份有效文件及当前未保存快照。
- 数据校验至少覆盖文件版本、项目/布局身份关系、窗格与标签结构、允许的内容类型、唯一窗格身份和有限数值尺寸。过大文件拒绝处理，并保留原字节。

### 4. 保存时机与异步归属

- 新建布局、窗格内容/标签操作、位置交换和尺寸拖动均进入同一保存流程。防抖约 600ms；本地缓存及时更新，文件保存状态独立记录。
- 排队时固定目录、项目身份、内容快照、几何快照、预期修订和保存序号。防抖执行时不得再从全局当前项目读取尺寸。
- 同一目录的保存串行执行，尚未开始的连续变化可合并为最新快照。较旧响应不能将较新修改标记为已经保存；上一次提交成功后，队列内下一份快照使用新的预期修订。
- 关闭或切换项目时立即提交该项目尚未发出的防抖快照，仍使用原项目快照；目录变更前同样先处理原目标。延迟响应不能覆盖已经切换到其他项目的界面或登记。
- 页面正常关闭可尝试提交，但不能承诺浏览器强制退出或进程被杀后仍能完成异步请求。只有文件提交确认后才显示已经保存；测试需覆盖等待保存确认后的关闭恢复。
- 从文件恢复的几何优先于旧浏览器尺寸缓存，且覆盖全部受支持尺寸。校验窗格对应关系并适配当前可用视口，不硬套已经不存在的窗格位置。

### 5. 原子写入与多写入方

- 主文件使用同目录临时文件加原子替换；建目录失败或写入失败时中止，不继续宣称成功。
- 对规范化后的实际项目目录执行读、校验预期修订、写入的串行事务。多个受支持进程写入同一目录时必须共用本地互斥机制；只用某一个服务进程内的队列不足以保护直接写文件的脚本。
- 所有受支持写入方在互斥范围内重读当前修订后提交。修订不匹配则返回冲突，保留当前文件和未保存草稿；界面提供重新加载、确认后重试的路径，不盲目自动覆盖。
- 旧文件首次创建同样要检查“不存在”的前置条件；另一个写入方已经创建主文件时不得覆盖。
- `bug-solver` 的布局工具改用同一固定文件、格式和写入协议。脚本保留备份、查看与修改能力，不再硬编码某个浏览器项目 ID 来定位文件。
- 直接用任意编辑器修改文件属于受控写入协议之外的操作，文件应在项目关闭后修改，再重新打开加载；本轮不承诺任意外部程序并发写入也不会丢修改。

### 6. 旧数据迁移与生命周期

- 读取顺序为：新主文件 → 可明确匹配的旧布局文件 → 原项目浏览器布局及尺寸缓存。新主文件存在但不可读或无效时停止自动迁移，不越过它用旧数据覆盖。
- 当前版本 1 旧文件须校验封装身份、布局结构及尺寸。存在旧项目映射时只取明确匹配的文件；无映射时仅在唯一有效来源下恢复，有多个来源则展示选择，不按时间猜测。
- 成功创建新主文件后再更新浏览器缓存和登记。旧文件保留，后续只写新主文件；失败可重试，重复迁移不能覆盖已经保存的新布局。
- 不批量清空 localStorage，也不批量迁移所有项目。某个项目第一次进入新流程时处理它自己的数据。
- 关闭项目、删除侧栏登记和删除磁盘布局分别处理。前两者不删除布局文件，也不删除应用实例、原生会话或业务数据。
- 项目目录变更视为选择新的保存目标：先完成原项目保存，再检查新目录的文件。新目录有布局时提示加载已有内容，不能直接覆盖。

### 7. 当前补丁处理及实施顺序

| 阶段 | 调整内容 | 可检查产物 |
| --- | --- | --- |
| A：核对分栏基础 | 核对初始化顺序的现有修正，完成仍有缺口的基础修复，保留已有项目和原生布局体验 | 原有分栏可打开，锚点与关闭恢复回归通过 |
| B：固定文件与存储模块 | 定义版本 2、固定文件、分类读取、完整快照、原子提交与冲突规则 | 在临时项目目录验证创建、重读、失败保留和冲突拒绝 |
| C：接入界面与恢复 | 接通全部内容和几何变更、保存状态、切换归属、从目录恢复和旧格式迁移 | 同一项目修改后落盘，关闭重开与无缓存恢复结果一致 |
| D：配套与文档 | 更新布局工具和使用说明，回写现有持久化说明 | 脚本与界面读写同一主文件；文档无“布局仅存浏览器”的过时现行说明 |
| E：真实安装验收 | 在隔离目录及测试宿主安装最终产物并走已确认用户流程 | 文件内容、UI 恢复和失败场景证据；分别记录自动化与真实宿主结果 |

左列多窗堆叠及新增预设已经在当前未提交内容中，但不作为布局落盘的必要前置。保留其差异，不顺手扩展；若随最终产物一起交付，必须分别验证编号、标签操作、尺寸分配及窄屏显示，未通过不能借持久化验收宣称整体通过。

## Testing Decisions

主验收接缝为真实安装的 Worktable 完整用户流程，用户已在 2026-10-26 明确回复“符合，按这个入口验收”。自动化从现有布局存储/受认证服务入口和真实分栏交互验证外部行为；复用既有锚点 DOM、服务端临时目录与应用标签回归的测试方式，不用源码字符串存在或构建成功替代验收。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 首次保存 | 项目生成一份固定主文件，名称不含浏览器项目 ID；文件能由新存储模块重读 |
| 内容与标签变化 | 添加、关闭、移动标签及切换选中项后，文件和重开后的界面与最终操作一致 |
| 仅调整尺寸 | 不再编辑内容，仅拖动各种分隔条，也会保存并恢复对应尺寸 |
| 关闭重开与宿主重启 | 等待已经保存后关闭并重新打开；测试宿主重启后仍恢复相同布局 |
| 无浏览器缓存 | 只清空专用测试浏览器缓存，重新选择项目目录即可恢复登记、布局和有效引用 |
| A/B 项目快速切换 | 防抖期间切换和异步响应乱序，两个文件的内容、目录和尺寸均不串用 |
| 文件优先 | 故意准备相冲突的旧浏览器尺寸；重开采用有效文件中的完整几何 |
| 旧格式与缓存迁移 | 分别以版本 1 旧文件、纯浏览器数据启动；生成新主文件，保留旧来源，再次打开不倒退 |
| 损坏/不兼容/读写失败 | 保留原文件字节，显示正确状态；不把错误当不存在，不显示虚假的保存成功 |
| 受支持并发写入 | 两个页面或界面与布局工具基于同一旧修订提交，仅一份成功；另一份明确冲突且可重试 |
| 外部工具修改 | 使用更新后的布局工具保存后重新打开项目，加载新布局且不被旧缓存覆盖 |
| 失效引用 | 应用或文件不存在时保留标签、说明原因；不伪造业务恢复、不新建会话 |
| 兼容与范围保护 | 无目录项目仍可用；关闭/移除登记不删文件；Windows、POSIX 与根目录拼接有回归 |

自动化需执行实际读写、恢复与冲突行为。并发用例必须覆盖跨受支持进程的写入场景，而非只验证单进程队列。真实宿主结果按实际宿主/平台记录，不将字符串路径测试外推为 macOS 或桌面全功能通过。

验收使用隔离的测试项目、浏览器和宿主；不得清空正式浏览器缓存或自动重启正式宿主。最终安装包按项目既有打包与安装验证流程生成，记录最终产物对应证据。

## Out of Scope

- 应用业务资料、应用实例存储、原生会话、轨迹、凭据与登录状态的完整备份或跨机器迁移。
- 一项目多套命名布局、历史版本管理界面、云同步和多人实时协作。
- 全盘项目发现、任意目录自动导入、项目副本的自动身份及引用重映射。
- 外部编辑器的实时文件监听与任意程序绕过写入协议后的并发保证。
- 借本轮持久化修复扩充布局引擎、新增更多预设，或改写其他应用的数据归属。
- 修复或提交无关的 ACL 恢复文件、预览图片和运行数据。

## Further Notes

本轮最小交付判断是：项目目录中的一份主文件足以恢复布局与必要登记，所有受支持布局操作都能可靠保存，并且失败、迁移和冲突不会静默覆盖已有文件。

用户已确认一项目一份固定布局文件及主验收入口，随后调用 implement-spec 授权实施及推送。规格整理阶段只编写方案；本轮后续已完成实现和最终包的真实 Windows Web 验收，尚待远程推送核对后关闭。详见[实施工单](worktable-project-layout/README.md)、[验收回执](worktable-project-layout/04-acceptance.md)及[两轴审查](worktable-project-layout/review.md)。正式 profile 未安装或重启，未发布远端 tag/Release。

本规格只调整项目布局持久化及恢复要求；已有应用、角色、任务与宿主升级的其他约束继续有效。

# Application-provided visual module directory

The real old-v4 Reading acceptance entry had no visual choice for its own reading-record-editor. Its renderer was registered, but both canvas cards and module type select used a fixed platform list. Requiring advanced JSON did not meet normal application authoring behavior.

The existing public registerRecipeModuleRenderer(id, view) now accepts an optional descriptor {title, appIds?}. The application supplies the title and applicable application IDs; platform code contains no Reading-specific condition. Both in-place canvas choices and module type selects observe the renderer catalog. Unregister removes the descriptor and renderer together; two-argument registrations remain compatible. Scoped renderers are unavailable in other applications, including runtime dependency projection. Existing unknown modules retain their identity rather than being silently changed.

Reading declares its own manager title and reading application scope. On an existing enabled v4 recipe, normal Select draft auto-advances to v5, Add module opens the visual directory, and choosing 阅读记录管理 adds only the new module. Save draft and preview leave running v4 intact. Preview is read-only. Only Activate draft replaces the running recipe, preserving original data connections, roles and existing modules.

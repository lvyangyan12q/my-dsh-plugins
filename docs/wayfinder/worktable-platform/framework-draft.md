# AI 工作台框架草案

状态：待共同审定的设计提案，不是已实现接口，不是已通过验收的规格。

## 已确认方向

以 Worktable 为代码基线；以 AI 工作台为主；既支持后续在工作台中设计应用，也支持直接开发应用后接入工作台管理。先定义稳定框架，降低后续扩展的相互影响。保留原生 DSH、既有应用私有能力、公共能力复用及现有数据。

用户进一步确认：一个工作项目可以组合使用多个应用；应用注册与业务能力应可被不同工作场景复用。应用可以提供完整页面或可嵌入模块；窗格只承载视图。同一实例在多窗格中共用状态，新建实例才形成新隔离上下文。跨项目遵循已确认原则：应用复用、工作状态和会话默认隔离、数据显式共享，不因隔离而复制整份资料。

## 本草案的目标

让新增应用主要通过注册和适配完成，尽量不改工作台核心。接口会演进，不承诺以后零改动；显式版本、能力探测和迁移规则承担演进成本。

## 建议分工

1. DSH 提供原生会话、模型、工具、轨迹、审批和停止；工作台通过兼容适配层调用，不复制实现、不修改原生仓库。
2. Worktable 外壳提供项目入口、布局、窗格、标签、标注、控制室和原生对话安排。维持一个窗口与布局所有者。
3. 平台内核提供应用注册、实例身份、生命周期、受控能力连接和持久化约定；不包含考公等具体业务。
4. 应用拥有业务界面、业务数据、业务规则和私有能力。页面搭建器也是平台上的一种应用接入方式，不是所有应用的必经入口。

## 优先确定的契约

| 契约 | 最小内容 | 约束 |
|---|---|---|
| 应用注册 | 稳定ID、显示名、版本、接入类型与入口、能力需求 | 接入分为独立网页、原生插件、组合配置；不强制业务应用改成配方 |
| 身份模型 | 应用定义、应用实例、页面、模块、项目关联 | Worktable项目与实例的最终映射仍待决定；布局位置不能充当稳定身份 |
| 生命周期 | 打开、显示/隐藏、关闭视图、停用、升级、卸载 | 关闭视图不等于取消任务；停用与卸载须有明确语义和释放规则 |
| AI连接 | 创建/绑定/打开会话、准备任务、观察状态、取消 | 用稳定身份找原生会话；有明确请求与错误反馈；展示模块可无角色 |
| 数据连接 | 数据源描述、读取、变更通知、可选业务动作 | 应用拥有数据；平台不任意读取其他应用存储；读写权限分开 |
| 存储与迁移 | 平台配置、布局偏好、业务数据分别归属 | 配置有schema版本；升级失败保留数据；卸载不默删业务数据；不全局替换历史路径 |
| 扩展与兼容 | 模块注册/注销、能力发现、接口版本、缺能力反馈 | 外部网页不能直接获得原生上下文、凭据或任意文件权限；不依赖DOM猜测作为应用协议 |

上述为接口责任清单，未锁定具体函数名称或参数。实施前需检验 Worktable 与 DSH 实际接缝，避免先设计不存在的能力。

## 接入层级建议

- 轻量网页：以URL打开，默认只是网页；跨域不可读内容、禁止iframe嵌入等限制明确反馈，必要时外部打开。需要平台能力时再使用经过来源、发送方、实例、能力和请求身份校验的桥接；不能只靠隐藏按钮控制权限。
- 深度插件：通过约定注册页面、模块、数据源与任务处理，沿用DSH的实际权限机制；只有声明并获准的能力可调用。
- 组合应用：通过布局、模块、数据与角色声明构成。运行时引用同一注册与身份规则，不另建第二套会话/窗口系统。

项目、应用、实例与视图的核心关系已确认：一个项目可以组合多应用，完整页面和可嵌入模块都是实例视图，窗格不创造新的实例。未归属实例及显式关联项目的原则已确认；具体选择器和挂载交互仍待原型验证。

## 状态与数据归属建议

- 平台Host拥有应用目录元数据、实例关联和需要耐久保存的平台配置。
- Worktable布局状态与浏览器展示偏好先按现状识别，迁移方案确认前不换存储、不清localStorage。
- 业务应用保留记录、资料和索引；DSH保留会话、轨迹、审批和附件。
- 明确任务运行状态、视图是否可见、是否有未读结果三者区别，不以Stop、会话完成或旧状态直接认定业务成功。

## 主题与交互契约建议

平台提供可复用的颜色、间距、字体、按钮、输入、状态、空态和错误态规则。组合模块及我们生成的页面采用这套规则；独立第三方网页不承诺自动改造成相同风格，也不通过全局CSS改写原生DSH。

## 建议实施顺序（尚不是实施工单）

先确认定位与项目/应用模型；再选定上游提交、宿主版本和兼容策略；做薄接入验证，分别接入一个独立网页与一个深度数据/角色应用；通过后才稳定第一版协议并渐进迁入现有能力。

每种接入至少验收：安装/打开、关闭重开、并发实例、缺能力反馈、真实原生执行、刷新/重启恢复、版本不兼容、升级失败/回退、停用/卸载后的数据保留。不能只用注册函数存在、构建成功或示例截图宣布接入成立。

## 保留的未决事项

未归属实例选择器与多视图挂载的实际验证；跨应用工作组织的具体交互；第一版桥接能力范围；配置是否与何时迁到Host；第一验证应用；原生公开限制如何反馈；旧123条要求与新路径的逐项映射。

## 第一版接入协议的建议结构（待审定）

以下只界定责任和错误行为，不代表已经存在的函数签名。

| 接入面 | 平台给应用什么 | 应用必须明确什么 |
|---|---|---|
| 注册 | 唯一身份校验、入口发现、版本与能力检查 | 应用ID/版本、入口、依赖及可选模块；显示名不作为身份 |
| 实例上下文 | 稳定实例身份、项目关联、可见性与生命周期通知 | 不以窗格序号或当前全局对话识别业务实例 |
| 视图与模块 | 挂载/激活/隐藏/释放通知、可用主题与布局约束 | 自有页面路由与可选可嵌入模块；网页可保留完整界面，不强制拆模块 |
| 数据 | 引用及连接生命周期、变更通知约定 | 真实数据所有者、作用范围、读取/可选写入动作与共享授权 |
| AI任务 | 原生能力适配、稳定会话关联、任务状态与取消反馈 | 目标角色、输入上下文、所需能力；准备不等于发送，停止不等于成功 |
| 持久化 | 平台配置/实例关联与存储故障反馈约定 | 业务数据迁移、数据版本、恢复责任；共享数据不能随单个实例关闭而删除 |
| 兼容与退出 | 不兼容/缺权限/缺能力的明确状态、注销与释放顺序 | 支持的协议版本、降级路径及升级/卸载后的数据保留规则 |

共享资源引用与实例状态必须区分；UI可见状态不能授予权限。跨实例共享数据不授予读取其他实例会话的能力。兼容路径只通过实际可用的原生接口，不能由协议提案凭空产生原生能力。

## 本轮接缝核对结论

用户确认采用：一个Worktable派生插件前台、同包内模块化平台内核、集中DSH适配、应用独立接入。下列源码事实限制了第一版的具体实现路线。

- Worktable已有 sidebar.worktable.project 项目插槽，传入reportMeta/reportUsed/openSplit/activeSplitId等ownerProps，可复用为第三方项目入口与布局接缝；不是完全没有扩展入口。它尚不是覆盖应用/实例/权限/生命周期的完整接入协议。
- 分栏使用模块级splitStore、单一setSplitEnv及全局分栏所有权协调，不能为每个应用复制一套引擎。保留单个布局所有者，在外层建立显式应用实例与视图关系。
- 内容类型仍是内部联合及渲染分支，不能把内部数据结构当作已发布模块注册协议；需在派生插件中建立受控注册层。
- 共享实例状态不等于可以重复挂载同一原生对话输入框。模型状态、会话身份、视图挂载与编辑器占用分别管理，必须用真实多视图验证。
- 本地Worktable仓库HEAD为0a9ff9d34eb2475b427bdfabe4321f53e27f9a2d，但源码、清单和lib有大量工作树修改，另有未跟踪桥接文件；本次事实对应本地混合快照，不等同该提交或GitHub主分支。基线固定必须先保存并核对用户改动，不能reset、clean或直接覆盖。

源码定位：Worktable的 src/client/index.tsx 项目插槽声明/订阅、ownerProps与openSplit；src/client/split.tsx 内容模型、SplitScope、setSplitEnv、splitStore及分栏所有权事件。详细研究单独保存，不将兼容版本声明外推为新组合实测通过。

现有平台迁移核对见[现有平台能力迁入前的边界核对](research/current-platform-migration.md)。上述研究没有改变产品、创建运行目录或执行迁移。

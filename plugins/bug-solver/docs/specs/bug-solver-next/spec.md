# bug-solver可靠性修复、同步优化与窗口4收集复盘规格

## Problem Statement

用户在Worktable中通过窗口1选择缺陷、窗口2维护SSH连接、窗口3编排修复和审核。目前主流程已有实现，但并发派发、重启恢复和产物路径隔离仍有可靠性缺陷；旧项目配置继续影响授权和派发，默认日志范围及连接缓存也与现有规格不一致。

窗口3重复请求完整运行数据和会话历史，并频繁重建页面。用户已经遇到下拉收起、输入中断以及方案正文滚动归零。滚动问题虽已定向修复，刷新机制仍需整体优化，不能依赖不断增加交互补丁。

审核结束后缺少实际可用的窗口4。用户需要收集需求及对应代码、处理过程和原始验证结果，复盘并沉淀知识，为后续优化skill和agent流程保留资料。用户最新明确：本期只收集和复盘，不以质量评分、流程优劣比较或评估运行系统为目标。

## Solution

先修复运行唯一性、恢复及文件边界，再统一页面刷新调度、按变化更新界面和增量读取消息。保持DSH原生会话作为真实执行入口；页面刷新失败不能重发业务动作或误报完成。

新增独立窗口4，沿用Worktable窗格和现有Host桥。用户选择明确任务，查看材料与缺失项，生成和编辑复盘，再按所选范围归档材料或提炼知识。复用co-dev Speckit的增量复盘、资产筛选和外部知识沉淀方法；不将工具链维护仓当作业务资料默认归档库。

本规格为本轮增量需求的唯一实施依据。已明确部分可先实施；尚未决定的范围以明确依赖阻塞对应任务，不阻塞独立修复，也不由实施者默认为已批准。

## User Stories

1. 作为缺陷处理人，我希望并发点击或跨标签派发同一缺陷只创建一个运行，以便避免重复修复。
2. 作为缺陷处理人，我希望同一仓库的占用检查与创建运行不可被并发绕过，以便保持串行约束。
3. 作为缺陷处理人，我希望相同请求重试返回原运行，以便网络抖动不产生新会话。
4. 作为缺陷处理人，我希望桥重启后恢复已绑定会话与待完成请求，以便正在运行的任务继续被正确追踪。
5. 作为缺陷处理人，我希望重启期间已经完成的任务能从权威记录恢复，以便页面不永久显示运行中。
6. 作为缺陷处理人，我希望结果无法确认时明确暂停且不自动重发，以便避免重复执行代码修改。
7. 作为缺陷处理人，我希望重复完成事件只推进一次状态，以便恢复和实时事件不会产生重复轮次。
8. 作为项目维护人，我希望产物读写不能通过目录链接逃出授权范围，以便其他目录不被读取或修改。
9. 作为项目维护人，我希望产物清单、实际读取和校验使用一致的路径边界，以便不能通过其他入口绕过检查。
10. 作为项目维护人，我希望允许访问的仓库只来自明确插件配置，以便保留旧SSH数据不会扩张权限。
11. 作为缺陷处理人，我希望派发只带SSH候选、不消费废弃项目映射，以便在窗口3明确指定仓库和分支。
12. 作为配置维护人，我希望窗口2修改连接后后续派发能读取新配置，以便不会连接到旧目标。
13. 作为配置维护人，我希望首次配置缺失不被永久缓存，以便新增连接后无需重开全部页面。
14. 作为缺陷处理人，我希望从窗口1派发也默认查询最近3天日志，以便入口不同不会改变排查范围。
15. 作为缺陷处理人，我希望明确修改的日志时间窗被保留，以便默认值不会覆盖我的选择。
16. 作为缺陷处理人，我希望手动刷新、轮询和操作后的同步不会重复拉取同一资源，以便页面稳定且响应及时。
17. 作为缺陷处理人，我希望切换运行后旧请求不能覆盖当前页面，以便看到的始终是所选任务。
18. 作为缺陷处理人，我希望实际运行中及时看到状态变化，以便知道何时需要处理。
19. 作为缺陷处理人，我希望等待人工确认时降低刷新频率，以便不为空闲任务持续高频请求。
20. 作为缺陷处理人，我希望结束运行停止高频详情同步，以便不浪费资源。
21. 作为缺陷处理人，我希望隐藏页面或窗格时减少同步、恢复可见时及时补读，以便兼顾资源和信息及时性。
22. 作为缺陷处理人，我希望网络异常时看到真实错误和数据更新时间，以便不把旧状态当作最新状态。
23. 作为缺陷处理人，我希望断线自动退避且手动重试立即生效，以便故障期间不持续高频失败。
24. 作为缺陷处理人，我希望数据未变化时不重建内容区，以便输入、选择和阅读不受干扰。
25. 作为缺陷处理人，我希望更新状态卡不会替换正在编辑的表单，以便不丢输入和光标。
26. 作为缺陷处理人，我希望方案、审核和产物正文保持阅读位置，以便长内容可以连续滚动查看。
27. 作为缺陷处理人，我希望查看历史对话时不被新消息强制拉到底部，以便读完历史上下文。
28. 作为缺陷处理人，我希望在消息底部时继续看到新增内容，以便跟随执行过程。
29. 作为缺陷处理人，我希望运行队列只加载必要摘要并支持历史分页，以便历史增多后仍可快速使用。
30. 作为缺陷处理人，我希望对话刷新只同步新增或更新内容，以便长会话不反复传输和解析全部历史。
31. 作为缺陷处理人，我希望加载更早消息保留当前阅读锚点，以便不会跳失正在看的位置。
32. 作为项目维护人，我希望消息缓存可在日志变化、重启或断线后正确重建，以便优化不造成遗漏或重复。
33. 作为项目维护人，我希望有优化前后的请求、传输和渲染证据，以便判断资源优化是否实际有效。
34. 作为配置维护人，我希望窗口1健康检查在无须展示时降频，以便减少后台请求。
35. 作为项目维护人，我希望一次性超时在操作完成或页面释放时清理，以便不会残留回调或未结束的读取。
36. 作为项目维护人，我希望先核实后台采集脚本是否仍在使用再优化，以便不修改废弃路径或启动额外进程。
37. 作为缺陷处理人，我希望窗口4独立挂载且刷新后保留，以便可与前三个窗口并列使用。
38. 作为缺陷处理人，我希望从已通过运行直接进入对应复盘，以便不用重新寻找材料。
39. 作为缺陷处理人，我希望收集清单关联明确run或历史任务，以便不会混入其他任务资料。
40. 作为缺陷处理人，我希望保留需求、方案、任务与代码版本的对应关系，以便后续能理解改动依据。
41. 作为缺陷处理人，我希望保留每轮方案、diff、原审核和后续确认，以便复盘偏差和返工。
42. 作为缺陷处理人，我希望收集真实测试结果、失败与未验范围，以便归档不把局部成功写成全部通过。
43. 作为缺陷处理人，我希望缺少spec、commit或其他材料时明确列出缺项，以便继续处理有依据的部分。
44. 作为缺陷处理人，我希望未提交材料记录工作区来源及内容标识，以便不会被冒充为某个已提交版本。
45. 作为缺陷处理人，我希望按现有Speckit方法生成增量复盘，以便不用维护第二套复盘框架。
46. 作为缺陷处理人，我希望每条结论带依据、适用范围、实际状态和行动，以便以后判断是否适用。
47. 作为缺陷处理人，我希望没有新增事实时复用已有结果，以便不会重复生成空报告或刷新日期。
48. 作为缺陷处理人，我希望在窗口4编辑并保存复盘到项目唯一归属，以便项目自己持有结论。
49. 作为缺陷处理人，我希望读取历史会话前明确范围和授权，以便只消费必要来源。
50. 作为缺陷处理人，我希望会话来源不可用时保留已读范围和缺口，以便不会把失败当作没有新内容。
51. 作为知识维护人，我希望项目知识候选与已确认规则分开，以便不把代码现状或推断自动变成通用规则。
52. 作为知识维护人，我希望按目标项目政策和明确目标定位知识库，以便不会写入错误的库。
53. 作为知识维护人，我希望查看目标库实际规则而不是固定文件名，以便不同库都能正确接入。
54. 作为知识维护人，我希望材料归档与知识文章提炼分别选择和报告，以便知道究竟完成了哪一步。
55. 作为知识维护人，我希望写入前看到准确来源、动作和目标清单，以便选择具体沉淀范围。
56. 作为知识维护人，我希望相同材料重复收集或归档不会产生重复快照，以便资料可持续维护。
57. 作为知识维护人，我希望部分失败可按未完成项重试并保留原件，以便不会覆盖成功结果或丢失来源。
58. 作为缺陷处理人，我希望未配置外部库时仍能完成项目内收集和复盘，以便独立工作不被阻塞。
59. 作为缺陷处理人，我希望复盘不改变窗口3的运行状态或新增审核轮次，以便职责清晰。
60. 作为流程维护人，我希望本期保存的需求和代码资料可供后续优化使用，以便不必现在就建立评分或比较系统。

## Implementation Decisions

### 既有架构和边界

- 保持Worktable承载HTML窗格、现有Host桥管理DSH会话的路线。修复与审核仍是原生会话，审核只读；不增加调度agent。
- 保留每轮方案确认、人工最终通过、只读SSH、脱敏、结果未知不自动重发、不自动合入的约束。资源优化不改变业务状态机语义。
- 已完成的正文滚动位置修复作为回归基线保留；后续局部渲染应减少节点替换，不能退回只靠全量重绘后恢复位置。

### 运行可靠性与配置

- DispatchService与RunStore协同把请求幂等、缺陷去重、仓库占用检查及首次记录变为原子保留操作。以规范化真实仓库身份去重；文件写入串行本身不足以实现此约束。
- 创建会话发生在保留运行之后。部分失败保留真实状态；结果未知不能释放占用后任意重复启动，必须先核对结果。失败释放与重试规则按可证明的执行状态处理。
- 桥启动时加载未结束记录、恢复绑定并核对权威会话事件；实时事件与重放去重，处理恢复期间的竞态。缺少足够证据时标明恢复受阻，不伪造完成，也不自动重发提示词。
- 产物读取、写入、列表及manifest校验共用真实路径边界；包含目录链接、父目录链接、尚未创建路径及检查/使用竞态。任何产物目标都必须仍属于授权仓库中的对应运行归属，不因链接后的新根而扩大范围。
- allowedRoots只来自明确插件配置。旧SSH项目和映射保留历史数据但不再参与权限、连接选择或仓库预填；不顺带删除用户历史配置。
- 窗口1派发前取得有效连接候选；连接保存后失效相关缓存，初次缺失不能永久缓存为空。跨窗口通知丢失时仍有重新读取路径。
- 统一最近3天的初始日志范围，并区分默认值与用户修改。spec支持仓库内外文件引用及无spec；页面提示与实际脏仓库/worktree策略保持一致。
- manifest错误目前只警告，不在本轮擅自升级为新的业务通过门禁；所有材料缺失和校验问题必须暴露给收集与复盘，审核通过不能等同材料完整。

### 同步调度与渲染

- 为页面设置单一同步协调器，合并轮询、手动刷新、切换运行及写操作完成后的读取。相同资源同一时刻最多一个请求在途，重复需求合并为必要的一次补读。
- 读取绑定run、角色和选择世代。切换或释放时取消过时读取，返回时再次核对身份；取消GET不取消Host任务，写操作绝不因同步失败自动重试。
- 状态分为执行中、等人、已结束/草稿、不可见、离线。执行中保持及时同步，等人降频，已结束停掉高频详情同步；列表采用较低频率。频率可配置，不与任务超时混用。
- 执行中2～3秒、等人10～15秒是调优起点，不是已确认的固定SLA；最终值由实际用户流程和测量确定。旧规格固定1.5秒/10秒要求由本增量的状态化调度取代。
- 同时处理浏览器可见性与Worktable内部窗格可见性。不能仅用浏览器hidden判断内部标签隐藏；若宿主没有可靠通知，必须保留有界低频兜底，不能让页面永久过期。
- 网络失败采用有上限的退避，手动重试与恢复可见立即补读；明确显示最后成功同步时间、离线/过期状态。卸载时释放计时器、监听、频道和在途读取。
- 写操作响应已含权威run时直接使用；只补读缺失或失效资源。列表、当前run、当前对话分别同步，不再每轮全量请求三者。
- 对比资源修订或有效内容后再更新相应区域。表单、方案正文、消息列表的节点在无须替换时保持稳定；保留焦点、输入法组合、选择范围和滚动位置。
- 对话在底部时跟随新增消息，阅读历史时不强制跳底；向前翻页按消息锚点保持位置。状态更新不得因长期编辑而完全不可见。

### 数据接口与缓存

- 运行列表使用摘要和分页，完整轮次与正文由详情提供。演进保持现有消费者可用，接口切换期间不把缺字段解释为状态丢失。
- run、列表与消息有各自可靠修订标识，不使用“每次请求更新时间”制造变化。消息变化不能只依赖run业务状态版本。
- 消息支持最新增量与向前历史两个方向，按稳定消息身份去重并支持已有消息更新。日志重置、截断或游标失效返回明确重同步信号。
- Host网关复用既有会话事件建立有界消息缓存或失效标记；首次访问与恢复时核对权威来源。避免每次请求都全量读取、重复脱敏和排序；缓存保留脱敏边界、大小限制与释放规则。
- SSE仅作为后续可选阶段：前两阶段测量后再决定。若采用，发送变化通知，页面合并拉取；保留鉴权、断线重连、版本补读、连接释放及低频兜底。不能把推送事件直接当成业务执行或完成证据。
- 窗口4复用这套同步机制，不复制新的高频循环；同页面协调器负责资源去重，跨iframe共享连接是否必要另按实际数量决定，不预先增加全局消息总线。

### 其他定时任务

- 保留提示消失、请求超时等必要的一次性计时。成功、失败、取消均清理；读取超时须终止底层请求，不能只有Promise超时而请求继续运行。
- 窗口1健康检查考虑可见性、用户主动拉取和故障退避；不为显示健康状态自动触发业务采集。
- 核实后台采集脚本的实际消费者和部署情况。仍在使用才改为配置变化触发与到期调度，保留低频核对作为通知丢失兜底；暂停采集不进行高频文件读取，不因规划启动任何后台进程。
- 终端发送前的短延迟先核实通道是否提供就绪信号；有可靠信号才替换，无信号则保留有界兼容延迟，不将所有定时器机械删除。

### 窗口4收集与复盘

- 2026-10-28收集范围已确认：允许手动选择成功、失败、中断的run及可识别的历史任务；收集已有需求、代码版本/diff、方案、原审核和真实验证结果，缺项明确展示。不默认复制整个仓库或完整会话。具体引用/快照与会话读取方式另行决定。

- 独立窗格、按run传递来源、按需启动原生复盘会话；复盘状态独立保存，不影响修复/审核状态。挂载使用实际项目、窗格、标签身份及布局修订校验，不能硬编码逻辑窗口编号覆盖已有内容。
- 复用co-dev当前spec-retro的增量归纳、spec-asset-curation的用途判断和external-knowledge的归档/提炼方法；窗口提供交互和编排，不复制成另一套方法。记录实际采用的方法来源和版本；方法不可用时报告缺口。
- 收集关联bug/需求、实际存在的规格/方案/任务、仓库身份、base与修复commit、diff和必要代码、逐轮方案、原审核及定向确认、真实测试结果及复盘。保留原始状态和后续处置关系，不重写为统一PASS。
- 未提交资料标工作区来源并记录内容hash；稳定版本引用不能仅靠分支名。缺失、未读、不适用和读取失败分别表达，不补造文件或结果。
- 复盘按实际出现的经验、领域、设计、Skill、Hook、代码问题归纳，包含结论、来源、适用范围、实际状态及行动。无新增不创建空报告、不刷新日期；普通bug不要求补齐完整Speckit流程。
- 项目当前定义和复盘保留唯一归属，bug-solver集中保存收集索引与按用途选择的材料。原需求与代码保持项目归属；具体快照范围待原决策票收口，不能默认复制全部仓库。
- 普通收集和预览不扫描全部历史，不运行会写游标的读取动作。DSH会话适配验证真实身份、来源格式、增量边界与副作用；只在授权范围读取，摘要成功保存后才确认消费进度。
- 知识库定位遵循目标项目政策和明确选择，兼容环境与Claude/Codex本地配置；只读取必要键。配置冲突明确提示，未配置不阻塞项目内复盘。
- 项目保存默认知识库及收集选项；单次复盘可临时覆盖，临时修改不自动更新项目默认值（2026-10-28用户确认）。目标库按实际规则接入；已核对的dcom-knowledge要求见[接入要求](../../wayfinder/window4-retro/knowledge-target-requirements.md)。
- 读取目标库真实导航与规范，不硬性要求固定政策文件名或同名技能。项目规则、原始材料归档与知识文章提炼分别处理；未确认通用性的结论留候选。
- 写回前展示精确来源、动作和目标，复用用户已明确选择的范围。相同内容幂等复用，来源变化生成新版本；部分失败保留源及已写内容，重试只处理仍在授权范围内的未完成项。
- 项目保存、raw归档、wiki发布各自记录结果；不自动改skill、清理原件、提交git或触发下一轮审核。spec-optimize是后续独立请求的消费者，本期不执行。
- 首期默认延续原规格的已通过运行入口。是否扩展失败/中断样本、历史任务导入的具体范围仍由原决策票确认，不将此前未回答的问题默认为接受。

## Testing Decisions

- 主验收接缝是实际Worktable窗格→Host桥→持久化结果的用户流程，覆盖选择缺陷、派发、方案确认、审核、重启恢复、复盘与所选知识写回。开发阶段复用已有页面假桥和桥服务测试；路径隔离使用临时文件系统夹具。用户于2026-10-28明确回复“符合，按此整理”，上述测试边界已确认。
- 好的测试断言外部行为：最终运行数量、实际会话调用、展示状态、文件范围与内容、可见更新和用户输入保留；不把实现函数名、固定DOM全文或精确计时器次数作为业务正确性。
- 并发测试使用受控屏障制造两个真实请求同时越过检查的场景，验证同缺陷去重、同仓库互斥、不同仓库可独立处理、失败与重试的占用规则。
- 恢复测试复用同一持久层重建服务，覆盖离线期间完成、恢复期间完成、重复事件、日志缺失和恢复结果未知；断言没有重复发送prompt。
- 文件夹具覆盖合法产物、链接越界、父目录链接、跨run路径、manifest引用、不存在的写入目标及大小限制；所有攻击目标是临时marker，不读取真实敏感文件。
- 页面回归复用现有冒烟测试，覆盖跨窗口连接更新、最近3天默认值、旧项目映射失效、慢响应与切换run乱序返回、刷新合并、失败退避、页面释放。
- 渲染行为必须增加真实浏览器验收：长方案滚动、历史对话锚点、文本选择、连续输入、输入法组合和下拉展开，跨多轮同步仍稳定。jsdom能证明属性保留，不能替代像素布局和真实滚轮验证。
- 消息与列表接口覆盖摘要/详情兼容、分页无重漏、增量内容更新、日志重置、缓存失效、脱敏及缓存释放；优化后不能丢掉历史或错误状态。
- 在相同数据、会话规模及操作脚本下记录优化前后请求数、返回字节、日志读取/解析量、内容区重建次数和状态延迟。无数据变化时不重复重建内容区，单资源不出现并发重复读取；不预先宣称固定收益百分比。
- 复盘测试通过注入会话与文件适配验证材料清单、来源版本、缺项、重复处理、保存失败和增量确认；沿用桥服务依赖注入方式，不新增多个只测内部细节的接缝。
- 知识写回使用临时模拟目标库验证不同政策、配置冲突、权限失败、重复归档、内容漂移、部分成功与精确范围；实际写库只有选定目标和范围后验收，不用真实知识库做破坏性夹具。
- 测试报告分别统计通过、失败、跳过；历史窗口1/2的81/81包含SKIP，不能当81项全部有效验收。源码、mock、本地浏览器、真实Host和业务验证分别记录。
